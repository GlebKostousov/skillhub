# Обоснование решений для защиты SkillHub

Дата: 2026-09-12

Этот документ хранит проверяемые основания решений, альтернативы и компромиссы. Это не журнал внутреннего хода мыслей: на защите важны требования, свидетельства, варианты и причины выбора.

## 1. Полный объём

Решение: выполнить обязательную часть, бонусный реестр, веб-интерфейс, живую проверку классификатора, сквозной модельный сценарий, учёт затрат, CI, Dockerfile и усиленные тесты.

Почему: дополнительные части проверяют не количество кода, а главный контракт задания в реальной цепочке. Каждая добавка должна либо подтверждать работоспособность скилла, либо защищать границу недоверенных данных.

Не делаем: микросервисы, PostgreSQL, Redis, очередь, сложную авторизацию и отдельный frontend-проект. Они не уменьшают риски задания.

## 2. Строгий Markdown, не JSON

Решение: протокол выдаётся в фиксированном Markdown, затем преобразуется в Pydantic-модель и Word.

Почему:

- Markdown читаем в чате и естественен для длинного текста модели.
- JSON удобен парсеру, но валидность синтаксиса не доказывает правильность фактов.
- По ExtractBench (2026) сложный structured output снизил валидность с 51% до 37%; это аргумент не против маленьких JSON-команд, а против упаковки длинного протокола в строгий JSON.
- Маленький ответ классификатора, напротив, оформляется структурированно: одно имя скилла или `null`.

Источники:

- <https://arxiv.org/html/2602.12247>
- <https://arxiv.org/html/2604.25359v1>

Подробно: [`../adr/0001-protocol-format-strict-markdown-2026-09-11.md`](../adr/0001-protocol-format-strict-markdown-2026-09-11.md).

## 3. Строгая структура, терпимое отсутствие данных

Решение: неизвестный заголовок, нарушенный порядок или кривая таблица — типизированная ошибка. Пустой раздел, неизвестный ответственный или срок — допустимые данные с каноническим `—`.

Почему: автоматический «ремонт» нарушил бы требование задания разбирать без эвристик. Одновременно пустые поля по заданию не должны ломать Word.

## 4. Открытые вопросы и интерактивные уточнения

Изначально пропуски только попадали в раздел «Открытые вопросы». После уточнения требования выбран интерактивный этап:

1. модель отмечает неизвестные поля через `—`;
2. приложение детерминированно строит вопросы для даты, участников, владельца и срока задачи;
3. пользователь отвечает или явно пропускает;
4. ответ обновляет конкретное поле `Protocol`; пропуск сохраняет стандартный сценарий.

Почему это не отдельный скилл:

- скилл — пользовательская способность и единица выбора классификатора;
- уточнение — состояние уже выбранного сценария;
- второй скилл создал бы неоднозначную классификацию и связал бы два промпта;
- управление состояниями, проверка и применение ответа надёжнее выполняются обычным кодом.

Почему вставка ответов не вызывает модель: место назначения ответа уже известно из `Clarification.target`. Это исключает дополнительную стоимость и новую поверхность prompt injection.

Пользователь может отдельно нажать «Собрать заново»: тогда первый черновик, ответы и запись встречи уходят в модель ещё раз. Штатный путь остаётся без модели.

## 5. Таблица уточнений

Решение: после обработки показывается таблица «Проблема / Ответ / Действия / Статус».

- Поле имеет подсказку и типовую проверку.
- `Отправить` принимает только корректное значение.
- `Пропустить` фиксирует осознанный пропуск.
- После выбора поле блокируется, появляется `Отменить выбор`.
- `Сформировать итоговый протокол` не продолжает процесс, пока есть хотя бы одна строка «Ожидает».
- Сервер повторяет проверку браузера.

Почему список, не пошаговый диалог: пользователь видит полный объём неопределённости, быстрее отвечает на несколько пунктов, а серверный контракт остаётся простым и пакетным.

## 6. Транскрипция — недоверенные данные

Решение: UI и HTTP разделяют `intent` и `material`. Классификатор видит только намерение и метаданные скиллов; материал передаётся только выбранному обработчику. Для режимов встречи материалом служит транскрипция.

Почему: транскрипция может содержать обычную речь, ошибки распознавания или специально вставленную команду «игнорируй инструкции». Если не передавать её классификатору, она физически не влияет на выбор скилла.

Правила смысла:

- обсуждение не равно решению;
- пожелание не равно задаче;
- отменённое решение не остаётся действующим;
- ответственный и срок не придумываются;
- несколько встреч не разделяются эвристически.

## 7. Защита модели

Невозможно доказать, что модель никогда не подчинится prompt injection. OWASP рекомендует уменьшать последствия:

- модель без инструментов, файлов, базы, произвольной сети и секретов;
- статический allowlist обработчиков;
- строгая проверка выхода;
- кодирование результата как текста;
- проверка человеком перед экспортом;
- лимиты размера, времени, токенов, параллельности и бюджета;
- отдельный adversarial eval.

Источник: OWASP Top 10 for LLM Applications 2025, LLM01, LLM05, LLM06:
<https://owasp.org/www-project-top-10-for-large-language-model-applications/>.

Блокирующее предупреждение о внешнем поставщике не показываем по решению владельца. Факт использования DeepSeek остаётся в README и конфигурации.

## 8. Архитектурный стиль из WMS

Переносим дисциплину:

- composition root в `app_factory.py`, без глобального изменяемого состояния;
- общий процессный шов для модульного запуска и публикации `skillhub.main:app`, без второго composition root;
- package-by-feature и фасады `__init__.py`;
- приватные `_*.py` и короткие файлы;
- тонкие HTTP-обработчики;
- кастомная иерархия исключений и централизованный HTTP handler;
- structlog, request ID и запрет значений неизвестных полей по умолчанию без обхода вложенных объектов;
- Python 3.13, строгий mypy, Ruff, import-linter;
- архитектурные и атакующие тесты-стражи;
- русские Google-style docstring.

Не переносим масштаб WMS: multitenancy, PostgreSQL, Redis, NATS, фоновые процессы, RBAC и SvelteKit. У SkillHub нет соответствующих нагрузок и доменных причин.

Примеры-источники: `C:\project\WMS\AGENTS.md`, `app/app_factory.py`, `app/core/exceptions/`, `app/core/logging/`, `pyproject.toml`.

## 8a. Семантическая файловая граница реестра

Решение: публичный пакет `skillhub.registry` экспортирует только
`SkillRegistry`, неизменяемые `Skill`, `LoadIssue`, `LoadReport` и предел одного
`SKILL.md`. Каждый вызов `load()` выполняет полное ограниченное чтение и
возвращает самостоятельный отчёт; состояние файлового дерева внутри объекта не
кэшируется.

Пути не считаются доказательством безопасности сами по себе: между строковой
проверкой и чтением объект можно заменить. Поэтому платформенные различия
скрыты за `RegistryFilesystem`, а загрузчик оперирует проверенным открытым
корнем, относительными операциями над потомками и конечными метаданными
открытого объекта. Ссылки разрешены только тогда, когда их фактическая цель
остаётся внутри того же доверенного корня. Это правило одинаково для POSIX,
Windows и явно настроенного UNC-корня; внешние цели и служебные пространства
имён закрывают путь до чтения.

Почему отчёт, а не исключение на первый дефект: один битый каталог не должен
скрывать корректные скиллы. Изоляция остаётся наблюдаемой через стабильную
причину без тела файла и абсолютного пути. При совпадении канонического имени
побеждает первый каталог в детерминированном порядке, поэтому результат не
зависит от порядка, возвращённого файловой системой, и не допускает молчаливой
перезаписи.

Почему лимиты фиксированы внутри модуля: это защитные бюджеты разбора и обхода,
а не пользовательская настройка продукта. Размер проверяется до декодирования
и YAML-разбора; число кандидатов, общий объём, глубина и работа со ссылками
ограничены до накопления неограниченного результата.

Для долгоживущего процесса состояние добавлено без изменения смысла `load()`:
он остаётся независимым чтением и не публикует результат. Только `reload()`
держит одну блокировку на протяжении полной доверенной загрузки, сборки нового
`RegistryCapture` и замены ссылки на поколение. Если блокировать лишь
присваивание, две параллельные загрузки могли бы завершиться в обратном
порядке и более старый результат стал бы текущим. Читатели блокировку не берут
и получают целый прежний отчёт вместе со снимком до публикации нового.

Каталог по HTTP не хранит второе поколение: страница «Скиллы» и каталог в
формате JSON каждый раз читают `capture()`. Одноразовый итог перезагрузки —
публичная проекция уже опубликованного отчёта, а не параллельный источник
истины.

Конструктор не принимает подменяемый загрузчик, а `reload()` напрямую вызывает
приватную модульную функцию, а не переопределяемый публичный `load()`. Так
публикация не обходит файловую политику и валидацию. История снимков, счётчик
версии и кэш нормализованных строк не добавлены: при ограничении в 128 скиллов
они создали бы второе состояние без пользовательской пользы.

## 9. Jinja2 + Bootstrap + JavaScript

Решение: одна серверная страница, локальный Bootstrap 5.3 и небольшой JavaScript-клиент API.

Альтернативы:

- HTMX не упрощает редактируемый документ, пакетную таблицу состояний и скачивание бинарного Word.
- Svelte/React требуют отдельной сборки и второго дерева зависимостей без пользы для двух экранов.
- чистый статический HTML теряет удобную серверную конфигурацию доступных возможностей.

Отдельного пользовательского CLI для бизнес-сценариев нет: он дублировал бы HTTP и не показывал бы ключевой сценарий на защите. Команда `python -m skillhub` только запускает локальный веб-сервер.

## 10. SQLite и стоимость

Решение: SQLite хранит только технический журнал вызовов и агрегаты. Текст встречи не сохраняется.

Почему SQLite:

- переживает перезапуск;
- транзакционно суммирует бюджет;
- не требует отдельного сервера;
- надёжнее конкурентной записи JSON Lines.

Стоимость считается из фактического `usage` ответа DeepSeek через `Decimal`, сохраняется в целых нано-единицах валюты. Запись содержит снимок тарифа, поэтому будущая правка YAML не меняет историю.

Цены вынесены в типизированный конфиг с `effective_from`, `verified_at` и `source_url`. На 2026-09-11 начальная модель — `deepseek-flash`; источник:
<https://api-docs.deepseek.com/quick_start/pricing>.

## 11. Точки расширения

Заранее реализуются только стабильные швы:

- `LlmGateway` для другого поставщика;
- конфигурация моделей и тарифов;
- `SkillHandlerRegistry` для новых доверенных обработчиков;
- версия грамматики протокола;
- фасад экспорта для будущего PDF;
- `Clarification` как будущий общий контракт разных скиллов;
- `UsageRepository` с SQLite-реализацией.

Не создаём заранее plugin framework, фоновые jobs, CRUD конфигурации через сайт, распределённый budget-store или multi-user auth. В архитектуре зафиксированы события, после которых они понадобятся.

## 12. Несколько настоящих скиллов и интерфейс ассистента

Первый макет был ориентирован на протокол. После сверки с формулировкой задания интерфейс сделан интерфейсом LLM-ассистента, а протокол — одним из его режимов.

Набор:

- `meeting-protocol` — полный протокол и Word;
- `meeting-action-items` — только задачи, ответственные и сроки;
- `text-summary` — краткое резюме произвольного текста;
- `text-translation` — перевод без анализа и изменения структуры;
- `business-message` — деловое письмо или сообщение по фактам.

Почему не оставить один скилл и искусственные записи:

- пользователь должен увидеть реальный выбор режима;
- близкие классы «протокол / задачи / резюме стенограммы» проверяют качество description;
- каждый режим можно выполнить и показать, а не только вернуть его имя;
- полный classifier matrix даёт измеримое доказательство вместо субъективной демонстрации.

Четыре простых режима используют общий `PromptSkillHandler`: различие находится в теле выбранного `SKILL.md`, как предполагает progressive disclosure. `meeting-protocol` имеет специализированный обработчик, потому что ему нужны строгий parser, уточнения и Word.

Интерфейс:

- боковая панель показывает доступные режимы, но не подменяет автоматический выбор;
- основная область содержит «Что нужно сделать» и «Материал для обработки»;
- после ответа виден фактически выбранный режим и стоимость;
- обычный скилл показывает текст; `meeting-protocol` включает таблицу уточнений и финальную выгрузку Word;
- отдельные разделы показывают реестр и расходы.

Ручной выбор режима не входит в первую версию: он скрывал бы ошибки классификатора на защите. Если позже понадобится override, он будет явным пользовательским решением и отдельной метрикой, а не тихим обходом.

## 13. Равные эпики и вертикальные слайсы

Решение: до начала кода программа разделена на шесть эпиков одинакового целевого веса. В каждом четыре слайса по две условные единицы. Слайс заканчивается наблюдаемым пользовательским результатом, проверкой и обновлением документации.

Почему не план по слоям:

- «сначала вся инфраструктура, потом весь backend, затем интерфейс» долго не даёт проверяемого результата;
- дефект интеграции обнаруживается в конце;
- трудно честно показать процент готовности;
- большие горизонтальные этапы провоцируют преждевременные абстракции.

Почему фундамент и безопасность всё же не отдельные финальные этапы:

- минимальный quality/security baseline появляется в первом запускаемом слайсе;
- каждый следующий слайс добавляет тест на новую границу;
- E6 не «начинает безопасность», а проводит adversarial проверку и усиливает уже существующие границы;
- инфраструктурная задача включается только вместе с пользовательским путём, который её оправдывает.

Зависимости допускают две независимые пары: после E1 параллельны классификатор и протокол; затем параллельны уточнения и учёт затрат. При последовательной работе порядок остаётся корректным.

Вес — средство выравнивания, а не обещание точных часов. После первого слайса калибруется фактическая скорость. Если слайс превышает две единицы более чем на 25%, он делится по наблюдаемой границе, но объём эпика не расширяется.

Подробно: [`../phases/skillhub-program.md`](../phases/skillhub-program.md).

## 14. Демонстрация после feature freeze

Решение: защита показывает as-built S1–S3 скриптом `eval/run_demo.py --offline`,
а не новыми пользовательскими маршрутами, CLI или постоянным хранением
транскрипций.

Почему скрипт, а не страница:

- пять режимов, protocol → уточнение → финал → DOCX, usage и сводка eval уже
  существуют в рантайме;
- повторяемость важнее сценического UI: временный журнал и байты DOCX не
  требуют ручной починки фикстур;
- каждый тезис защиты опирается на `tests/security/`, `tests/eval/`,
  `tests/delivery/` или на явное ограничение в threat model.

Не обещаем, что модель невозможно подчинить prompt injection. Офлайн-eval
разделяет обход границы и остаточную смысловую ошибку. Живой вызов модели не
условие merge.
