`reload()` намеренно держит единственный writer-lock на протяжении полной
загрузки, построения отображения и атомарной публикации. Поэтому одновременно
активна только одна ограниченная загрузка; `snapshot` и `search()` этот lock не
берут. Публикация копирует и сортирует только ссылки не более чем на 128
`Skill`, а не строки или тела документов. Внутренней истории снимков нет.

Статических пределов достаточно: benchmark не запускался, тесты не запускались.
Проверен committed delta из одного коммита `58e2750`; изменения рабочей копии в

# Обозначения и унаследованные пределы

- `n <= 128` — число `Skill` в отчёте/снимке;
- `q` — число вызовов поиска;
- `r` — число вызовов `reload`;
- `p` — число чтений свойства `snapshot`;
- `m <= n` — число результатов одного поиска;
- `ell` — длина одного query после `casefold`;
- `a <= 64` — максимальная длина канонического имени;
- `X = sum(len(name) + len(caption))` по снимку;
- `M` — память графа значений одного снимка, включая body и metadata;
- `tau_i` — wall time загрузки `i`, включая файловые системные вызовы;
- `h <= r + 1` — число поколений снимка, ссылки на которые удерживает внешний
  код.

E1-S3 не меняет loader. Сохраняются пределы E1-S2: не более 256 root entries,
128 попыток каталогов, 65 536 байт одного `SKILL.md`, 1 048 576 байт всех
документов, 1 024 auxiliary entries на каталог, глубина 32, 256 resolver steps
и 40 link hops на один `open_child`. Поэтому `X=O(1_048_576)` и
`M=O(1_048_576)` с постоянными накладными расходами Python.

Обозначим унаследованную работу полной загрузки как:

`F = O(K + 256 log 256 + T + E + U * resolver_cost)`,

где `K` — суммарная длина root-имён, `T <= 1_048_576`, `E <= 128 * 1_024`, а
`U` — ограниченное число открытий компонентов. Память загрузчика остаётся
`O(T + K + 256 + 1_024 + depth/buffer + resolver state)`. Это bounds на объём
работы и ресурсов, но не на wall time: локальный или сетевой syscall не имеет
прикладного deadline.

# Lock, публикация и удержание памяти

Критическая секция в `_registry.py:88-91` равна полной операции:

`tau_i + O(n log n * a) + O(n)`.

В неё входят filesystem I/O, parsing, `sorted(report.skills)`, создание `dict`,
`MappingProxyType` и одно присваивание `_snapshot`. Это соответствует договору
сериализации reload и не задерживает читателей. Сужение lock только до
присваивания позволило бы параллельные полные загрузки и публикацию устаревшего
результата после более нового.

Для `r` конкурирующих reload:

- активен один loader, остальные writers ждут;
- суммарная работа `O(r * (F + n log n))`;
- завершение всей очереди занимает
  `sum(tau_i + O(n log n))`;
- ожидание конкретного writer зависит от уже захвативших lock вызовов; строгой
  границы ожидания и fairness нет, потому что `threading.Lock` их не обещает и
  syscall может не завершиться;
- readers имеют нулевую конкуренцию за прикладной lock, хотя обычная
  конкуренция за GIL/CPU остаётся.

`sorted()` создаёт временный список `O(n)` ссылок, comprehension — новый
`dict` `O(n)`, а `MappingProxyType` не копирует dict. Ключи — уже существующие
`skill.name`, значения — те же `Skill`, что в `LoadReport`; body/caption не
копируются. В момент публикации одновременно живут старый снимок, новый report,
временный sorted-list и новый dict: `O(M_old + M_new + n)`.

После присваивания реестр хранит только новое поколение. Старые снимки
освобождаются после ухода внешних ссылок. Если вызывающий намеренно сохраняет
`h` старых snapshot/report/search-result, удержание составляет
`O(h * (M + n))`; это владение вызывающего, а не внутренняя утечка. Без таких
ссылок `r` повторных reload не накапливают память: peak остаётся
`O(M_old + M_new + n)`. Неизменившийся каталог всё равно перечитывается и
публикует новый dict, то есть экономии по identity нет, но пределы сохраняются.

# Поиск

`search()` один раз вычисляет `query.casefold()`, один раз захватывает ссылку на
текущий mapping и проходит его в каноническом insertion order. Для каждого
элемента `name.casefold()` вычисляется заново; `caption.casefold()` вычисляется
только если имя не совпало. Нормализованные строки не кешируются.

Один общий worst case — `O(ell + X + n * ell)` времени: casefold полей линеен,
а каждый отдельный substring search может учитывать длину pattern. Пиковая
дополнительная память — `O(ell + f + m)`, где `f` — длина текущей временной
casefold-строки. Для `q` поисков с максимальной длиной query `ell_max`:

`O(q * (X + n * ell_max))` времени без накопления нормализованных полей.

Пустой query также сканирует снимок и casefold-ит все имена, но благодаря
short-circuit не трогает captions; это не проблема при `n <= 128` и `a <= 64`.
Даже worst-case scan captions ограничен общим байтовым бюджетом E1-S2.

| `p` чтений `snapshot` | `O(p)` | `O(1)` без удержания, `O(p)` ссылок при удержании | Не ждёт reload |
| `snapshot[key]` | average `O(1)`, theoretical `O(n)` | `O(1)` | Dict под proxy, `n <= 128` |

| `load()`, injected loader | стоимость injected callable | его результат | Lock отсутствует; приватная test seam |
| `load()`, missing/unreadable root | работа до отказа | один `LoadIssue` | Ожидаемая ошибка преобразуется в report |
| `load()`, empty root | один bounded root-open/enumeration | пустые tuples | Унаследованные filesystem bounds |
| `load()`, normal/частично битый root | `F` | унаследованная bounded memory, output `O(M+n)` | Не публикует snapshot |
| `load()`, byte/entry/depth/resolver limit | работа до соответствующего жёсткого счётчика | в тех же bounds | Нет retry/backoff |

| `reload()`, ожидаемый loader failure | работа до failure + `O(1)` | старый + пустой новый snapshot | Публикует предсказуемый пустой report |
| `reload()`, неожиданное исключение | работа до исключения | transient loader state | Context manager освобождает lock; старый snapshot остаётся |

| `q` поисков | `O(q * (X + n * ell_max))` | `O(q*n)` только если caller удерживает результаты | Каждый вызов захватывает ровно одно поколение |
