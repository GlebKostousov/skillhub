Обе находки reviewer rework-2 закрыты в заявленном основном сценарии:
Windows открывает обычного потомка от переданного родительского дескриптора,
а прежний 791-строчный модуль разделён по ABI, операциям с дескрипторами,
перечислению, разбору reparse data и разрешению пути. Итеративные resolver
используют один общий накопительный бюджет и одновременно владеют не более чем
одним промежуточным дескриптором.

Gate всё ещё блокирует смежный случай доверенного UNC-root: абсолютная
внутренняя ссылка на тот же share ошибочно отклоняется только из-за UNC-формы
цели. Кроме того, после перехода на единый реальный вход в Windows resolver
остался второй вход без production-вызовов.

## A. Дефекты / риски

- [P2] [E1-S2-R3-REV-001]
  [`src/skillhub/registry/_windows_reparse.py:36-66,156-182,189-200`;
  `src/skillhub/registry/_windows_resolver.py:114-130`] →
  обычный потомок доверенного `\\server\share\skills` теперь корректно
  открывается относительно `parent`, но абсолютная внутренняя цель ссылки
  `\??\UNC\server\share\skills\shared` не доходит до уже существующей проверки
  `commonpath`: `_normalized_absolute_target()` сначала безусловно отклоняет
  любую UNC-форму. В результате семантически одинаковая относительная ссылка
  `..\shared` разрешается внутри UNC-root, а абсолютная ссылка на тот же объект
  получает `UnsafePathError`. Это расходится с договором E1-S2, где запрещена
  ссылка, **выходящая** за root, а внутренняя ссылка сохраняет обычное поведение.
  Точечный вызов `target_components()` подтвердил отказ для обеих форм
  `\??\UNC\server\share\skills\shared` и
  `\\server\share\skills\shared` при таком же UNC-root →
  нормализовать UNC substitute name, затем сравнивать share и containment с
  доверенным UNC-root; UNC при локальном root, другой share и device namespace
  по-прежнему отклонять до открытия цели.

- [P3] [E1-S2-R3-REV-002]
  [`src/skillhub/registry/_windows_resolver.py:32-60`] →
  production-путь входит через `open_child()` и передаёт реальный `parent` в
  `_resolve_components()`, но рядом сохранён `_open_components()`, который
  создаёт второй бюджет, всегда начинает от `root` и принимает отдельный
  параметр `hops`. Поиск по Python-коду не нашёл вызывающего production-кода;
  функция доступна только как альтернативный внутренний шов. Она возвращает
  ровно ту форму входа, от которой рефакторинг отказался ради единой
  parent-семантики, и оставляет две точки инициализации одного state machine →
  удалить неиспользуемый вход и оставить `open_child()` единственным владельцем
  создания бюджета.

## B. System design

- Parent semantics: `open_child(root, parent, name)` на обеих платформах
  начинает обход от переданного открытого `parent`. Для обычного компонента
  Windows больше не восстанавливает абсолютный путь и не повторяет поиск от
  root. Основная `E1-S2-R2-REV-001` закрыта.
- Trusted UNC: обычный каталог и файл под доверенным UNC-root используют
  относительный `NtCreateFile`; политика недоверенной reparse-target к ним
  больше не применяется. Остаточный P2 относится только к абсолютной
  внутренней цели самой ссылки.
- Iterative resolver: POSIX и Windows хранят `deque`, проходят её через цикл и
  при переходе по ссылке заменяют очередь компонентами от root. Рекурсивного
  descent и удержания цепочки родительских дескрипторов больше нет.
- Shared budget: `ResolutionBudget` — один источник пределов 256 совокупных
  шагов и 40 переходов по ссылкам. И посещение компонента, и follow расходуют
  тот же объект; новая очередь проверяется против уже израсходованного остатка.
- Resources: probe-дескриптор Windows закрывается в `finally`, raced reparse
  token закрывается до повторного разрешения, текущий owned parent закрывается
  при замене и на любом выходе. POSIX применяет ту же модель владения. Нового
  пути утечки в delta не найдено.
- API: `registry.__init__` по-прежнему экспортирует только
  `SkillRegistry`, неизменяемые модели и `MAX_SKILL_FILE_BYTES`.
  `ResolutionBudget`, Win32 ABI и platform operations остаются приватными.

## C. Архитектура относительно канона

Направление `core ← registry ← web` и семантическая граница
`RegistryFilesystem` сохранены. `_registry.py` не знает о нативных
дескрипторах, resolver или ABI; доменный порядок, duplicate policy и parser
не дублируются в платформенных модулях.

Разделение Windows backend соответствует причинам изменения:
`_windows_abi.py` владеет объявлениями ctypes, `_windows_handles.py` —
открытием/чтением/metadata, `_windows_directory.py` — перечислением,
`_windows_reparse.py` — чистым разбором и нормализацией цели,
`_windows_resolver.py` — state machine, а 11-строчный `_windows_io.py` собирает
прежний `PlatformAdapter`. Нового публичного слоя или protocol-иерархии не
появилось; основная `E1-S2-R2-REV-002` закрыта.

Архитектурный остаток мал и локален: `_open_components()` создаёт второй вход в
resolver без отдельной production-причины изменения. После его удаления у
Windows backend останется одна точка parent-relative разрешения и один общий
источник бюджетных инвариантов.

## D. Читаемость и «Как это работает (просто)»

Верхний путь читается линейно: открыть подтверждённый root → перечислить
кандидатов → открыть кандидата от root handle → открыть `SKILL.md` от handle
кандидата → ограниченно прочитать → разобрать → проверить имя → определить
`has_files`.

Как это работает (просто): обычный файл открывается непосредственно внутри уже
открытого родителя. Если запись является ссылкой, система сначала открывает
саму ссылку без перехода, читает её цель, сводит безопасную внутреннюю цель к
компонентам от корня и проходит их циклом. Один счётчик ограничивает всю эту
работу, включая повторные переходы, а промежуточный каталог всегда только один.

Деление Win32-кода сделало эту последовательность заметно проще: ABI, работа с
дескриптором, разбор буфера и алгоритм больше не перемешаны. Читаемость
ухудшают только мёртвый второй вход `_open_components()` и скрытая асимметрия,
при которой относительная UNC-ссылка принимается, а равнозначная абсолютная —
нет.
