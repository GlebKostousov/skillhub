## B. System design

- Place / SoT: `SkillRegistry` остаётся единственным публичным поведением
  слайса. `_registry.py` владеет порядком и сборкой отчёта, `_document.py` —
  форматом `SKILL.md`, `_filesystem.py` — containment и бюджетами обхода,
  `_posix_io.py` / `_windows_io.py` — только нативными системными вызовами.
  Политика не продублирована между платформами.
- Contracts / immutable data: `Skill`, `LoadIssue` и `LoadReport` по-прежнему
  являются `frozen=True, slots=True`; их поля состоят из строк, `bool` и
  кортежей, поэтому наружу не выходит изменяемое состояние загрузки
  (`src/skillhub/registry/_models.py:6-48`). Общий `Handle` также неизменяем,
  а его жизненный цикл скрыт context manager.
- Cross-platform adapter: POSIX открывает потомка через `dir_fd`, получает тип
  и identity через `fstat`, читает тот же descriptor и использует
  `O_NONBLOCK|O_CLOEXEC`. Windows открывает через `CreateFileW`, получает
  нормализованный final path, volume/file ID и тип из открытого HANDLE, а
  чтение и перечисление выполняет через этот HANDLE. Оба backend закрывают
  ресурс и на штатном выходе, и при ошибке построения `Handle`
  (`src/skillhub/registry/_filesystem.py:38-54`,
  `src/skillhub/registry/_posix_io.py:40-123`,
  `src/skillhub/registry/_windows_io.py:122-238`).
- Errors / observability: per-entry причины остаются у безопасного
  относительного идентификатора; общий предел числа записей, попыток или
  байтов даёт один `registry_limit_exceeded` на `"."` и прекращает дальнейшую
  работу. Предел auxiliary tree даёт локальный `directory_limit_exceeded`.
  Исходные исключения, пути и содержимое не попадают в `LoadReport` или
  `registry.skill_skipped`.
- Determinism / resources: root overflow отвергается до parser work и без
  частичного результата. Остальные записи идут в стабильном отсортированном
  порядке; число попыток, суммарные parser bytes, auxiliary entries и depth
  имеют численные границы. Identity-set устраняет повторный обход физических
  каталогов, а byte limit применяется до decode/YAML.

## C. Архитектура относительно канона

Направление `core ← registry ← web` сохранено: production-дельта реестра не
импортирует `web`, composition root или будущие прикладные пакеты. Публичный
`registry/__init__.py` экспортирует модели, фасад и явно документированные
ресурсные константы; детали parser, handle и backend остаются приватными.

Разделение оправдано разными причинами изменения: YAML-схема не зависит от
Win32/POSIX, общая файловая политика не копирует нативные вызовы, а выбор
backend происходит один раз по `os.name`. Хотя Win32 FFI занимает 292 строки,
это преимущественно декларации ABI и один связный адаптер; дробление
структур, функций открытия и перечисления на дополнительные модули увеличило
бы навигацию без новой границы. Преждевременных repository/port/plugin/service
абстракций не добавлено.

## D. Читаемость и «Как это работает (просто)»

Happy path теперь читается сверху вниз: открыть корень → получить ограниченный
и отсортированный список → открыть каталог → прочитать ограниченный
`SKILL.md` → разобрать поля → проверить уникальность → определить
`has_files` → создать неизменяемый `Skill`. Ожидаемые отказы проходят через
один `InvalidSkillError`, а root-level overflow выделен отдельно. Повторение
между backend ограничено неизбежной реализацией общего `PlatformAdapter`.

Как это работает (просто): реестр открывает не просто имя пути, а реальный
файловый объект, проверяет, где он оказался и какого он типа, и только потом
читает его. Один битый каталог становится короткой причиной пропуска. Если два
каталога объявляют одно имя, остаётся первый по стабильному порядку. При
внутренней ссылке обход продолжается, при внешней — цель не читается, а цикл
останавливается по identity.
