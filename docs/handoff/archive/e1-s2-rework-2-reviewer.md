# Выжимка

Роль: reviewer
Scope: `3bd870b..6089e28`
Вердикт: НУЖНА_ДОРАБОТКА
Находки: 2 — P0: 0, P1: 0, P2: 2, P3: 0.

Root race и прежняя follow-before-containment проблема закрыты для локального
дерева: фактически открытый root сверяется с ожидаемым до перечисления, а
каждый компонент ссылки проверяется без следования. Семантический файловый
фасад также закрыл прежнее протекание `Handle` в оркестрацию. Gate всё ещё
блокируют сломанная загрузка с доверенного UNC-root на Windows и новый
791-строчный Win32-модуль, смешавший ABI, I/O, разбор reparse data, разрешение
ссылок и файловую политику.

## A. Дефекты / риски

- [P2] [E1-S2-R2-REV-001]
  [`src/skillhub/registry/_windows_io.py:224-242,635-700,741-749`] →
  `open_path()` явно умеет открыть UNC-root через `\\?\UNC\...`, но
  `open_child()` превращает обычный путь `parent.final_path / name` в
  абсолютную цель и передаёт его в `_target_components(relative=False)`.
  Далее `_normalized_absolute_target()` безусловно отвергает любой путь,
  начинающийся с `\\`. Поэтому у валидного доверенного корня
  `\\server\share\skills` перечисление проходит, но открытие каждого обычного
  дочернего каталога завершается `UnsafePathError`, а отчёт не содержит ни
  одного валидного скилла. Проверка недоверенной reparse-target ошибочно
  применена к обычному потомку уже принятого root → строить начальные
  компоненты непосредственно относительно root/parent handle, а запрет
  UNC/device namespace применять только к данным, прочитанным из reparse
  point. Это сохраняет no-follow для внешних ссылок и не запрещает
  настроенный владельцем UNC-root.

- [P2] [E1-S2-R2-REV-002]
  [`src/skillhub/registry/_windows_io.py:11-207,210-500,510-712,725-791`;
  `src/skillhub/registry/_posix_io.py:40-48,122-202`;
  `docs/architecture/decision-rationale.md:100-116`] → Windows adapter вырос
  с 292 до 791 строки и теперь одновременно определяет ctypes ABI, выполняет
  native open/read/enumeration, разбирает бинарный reparse buffer, нормализует
  NT/DOS/UNC paths, реализует state machine разрешения ссылок и управляет
  ресурсами. Алгоритм `hops + remaining components + rooted component walk` и
  его пределы параллельно реализованы в POSIX adapter. Это уже не короткий
  платформенный адаптер: изменение одной no-follow гарантии требует
  согласованно править несколько удалённых участков большого FFI-файла и
  вторую реализацию, а дефект E1-S2-R2-REV-001 возник именно из-за смешения
  доверенного child-path с политикой недоверенной reparse-target → оставить
  `RegistryFilesystem` единственной семантической границей, но разделить
  Windows internals как минимум на ABI/buffer declarations, чистый
  reparse-target parser/normalizer и handle I/O/resolver. Общие hop/component
  инварианты должны иметь один приватный источник истины; наружу новые типы и
  функции экспортировать не нужно.

## B. System design

- Place / facade: `_registry.py` теперь видит только
  `open_registry()`, `list_candidates()`, `read_skill()` и
  `has_additional_files()`. Containment, descriptor lifecycle, identities и
  бюджеты обхода скрыты в `RegistryFilesystem`; прежняя цепочка одношаговых
  `_load_*` схлопнута. Это закрывает rework-1 logic-simple finding.
- Root / no-follow: `SkillRegistry.load()` делает strict resolve, а
  `open_registry()` сравнивает нормализованный `final_path` того же открытого
  root handle до первого `iter_entries`. POSIX добавил `O_NOFOLLOW` и вручную
  открывает подтверждённые внутренние компоненты от root descriptor. Windows
  использует `FILE_FLAG_OPEN_REPARSE_POINT` / `FILE_OPEN_REPARSE_POINT`,
  читает reparse data до следования и открывает подтверждённые компоненты
  относительно root handle. Для локальных путей прежние root-race и
  follow-before-check устранены.
- Contracts / API: публичный пакет снова экспортирует только модели, фасад и
  подтверждённый внешний предел `MAX_SKILL_FILE_BYTES`; остальные бюджеты
  приватны. `Handle`, `PlatformAdapter`, `_SkillRead` и platform operations не
  вышли в публичный API.
- Errors / cleanup: root, candidate, `SKILL.md`, промежуточные компоненты и
  auxiliary handles закрываются в `finally` либо в локальной ветке ошибки.
  `_make_handle()` на обеих платформах закрывает token при сбое metadata.
  Ожидаемые ошибки кандидата остаются локальным `LoadIssue`, а общий предел
  останавливает загрузку одним root issue. Нового пути утечки ресурса в delta
  не найдено.
- SoT / determinism: parser остаётся единственным владельцем формата
  `SKILL.md`; сортировка, first-successful duplicate policy и immutable
  модели не изменены. Незакрытая системная проблема — platform policy
  рассредоточена между двумя resolver implementations, а на Windows ещё и
  внутри одного чрезмерно широкого файла.

## C. Архитектура относительно канона

Направление `core ← registry ← web` сохранено. `_registry.py` отвечает за
порядок и доменный отчёт, `_document.py` — за формат, `_filesystem.py` — за
семантическую файловую политику; это хорошие глубокие границы. Новых
repository/service/plugin abstractions и публичных platform contracts нет.

Отклонение локализовано ниже фасада. Канон требует приватные короткие файлы,
но `_windows_io.py` стал самостоятельной подсистемой из нескольких причин
изменения. Деление здесь не вернёт прежний helper zoo: registry продолжит
зависеть от одного `PlatformAdapter`, а новые Windows-модули будут деталями
одного backend. Одновременно такое деление позволит отделить чистую проверку
reparse-target от открытия обычного доверенного потомка и устранить
E1-S2-R2-REV-001 без новых публичных швов.

## D. Читаемость и «Как это работает (просто)»

Верхний happy path теперь читается линейно: разрешить и открыть root →
получить стабильный список кандидатов → ограниченно прочитать `SKILL.md` →
разобрать поля → проверить уникальность → определить `has_files` → вернуть
неизменяемый отчёт. `_registry.py` уменьшен до 157 строк, и нативные handles в
нём больше не видны.

Как это работает (просто): реестр держит открытый корень как якорь. Ссылку он
сначала открывает как саму ссылку, читает её цель, убеждается, что цель внутри
якоря, и лишь затем проходит путь по одному компоненту. Это не даёт внешней
ссылке инициировать чтение. На Windows тот же код сейчас ошибочно считает
обычный дочерний путь внутри доверенного сетевого корня «внешней UNC-целью»,
а понять и исправить различие трудно из-за пяти смешанных обязанностей в
одном 791-строчном модуле.
