## A. Дефекты / риски

- [P2] [E1-S4-REV-001]
  [`src/skillhub/web/routes.py:91-126,204-215,245-255`;
  `src/skillhub/registry/_registry.py:69-78`] → web хранит текущий каталог в
  двух независимо публикуемых значениях. `SkillRegistry.reload()` сначала
  заменяет `_snapshot`, затем `_CatalogState.reload()` отдельно строит и
  присваивает `_summary`. Обычный `GET /skills` без общего снимка сначала
  вызывает `registry.search(q)`, потом читает `catalog.summary`; POST после
  выхода из `_CatalogState`-lock отдельно снова читает реестр. Поэтому
  параллельный GET/reload может показать новые карточки со старым
  `loaded/skipped/issues` либо старые карточки с новым предупреждением, а два
  одновременных POST могут вернуть итог одной загрузки с карточками следующей.
  Например, после исправления отсутствующего root страница способна кратко
  показать пять карточек вместе со старым `root_missing`; при обратном
  переходе пустой каталог может оказаться без актуального предупреждения →
  публиковать список и связанный `ReloadSummary` одним неизменяемым
  поколением и строить API/UI/ответ POST из одной захваченной версии, сохранив
  один источник истины для семантики поиска.

- [P2] [E1-S4-REV-002]
  [`src/skillhub/web/routes.py:18-351`;
  `src/skillhub/web/security.py:26-215`] → один `routes.py` вырос с 53 до
  351 строки и одновременно владеет публичными DTO, состоянием reload,
  обработчиками, регистрацией маршрутов, преобразованием domain → HTTP и
  сборкой template context. В нём уже два способа проверить тот же предел
  query (`_require_valid_query()` и ручной `len(q)`), а почти одинаковый
  `_SkillsPageContext` собирается в трёх местах. `security.py` в том же
  коммите объединяет новый протокол reload-формы и origin-parser с прежним
  middleware заголовков/request-id. Низкая цикломатическая сложность отдельных
  функций не устраняет несколько причин изменения и не соответствует канону
  тонкого `web` с короткими приватными файлами → оставить `routes.py` тонкой
  регистрацией/HTTP-оркестрацией, вынести приватные DTO + атомарное
  catalog-view и reload-request guard по отдельным внутренним швам, а query и
  сборку page context свести к одной реализации без нового публичного слоя.

## B. System design

- Composition root по внешним зависимостям сохранён: `app_factory.py` создаёт
  один `SkillRegistry`, выполняет начальный reload, генерирует отдельный
  CSRF-токен экземпляра и передаёт готовые зависимости в `web`. `main.py` и
  process startup в диапазоне не менялись.
- Проблема владения состоянием локализована ниже root: `_CatalogState`
  добавляет второй lock и второй указатель состояния рядом с уже атомарным
  снимком `SkillRegistry`. Этот дополнительный владелец не образует одну
  транзакцию чтения с registry и приводит к E1-S4-REV-001.
- HTTP-границы в остальном ясны: HTML живёт на `GET /skills`, интеграционный
  JSON — на `GET /api/skills`, мутация — на `POST /skills/reload`.
  `SkillSummary` раскрывает только `name`, `caption`, `description` и
  `has_files`; `ReloadSummary` содержит только счётчики и безопасные
  `path/reason`. `body` и абсолютный root не переходят в HTTP.
- Пустой query возвращает весь снимок, поиск делегирован
  `SkillRegistry.search()`, длинный query получает стабильный 422; HTML не
  отражает исходную длинную строку. Missing root остаётся штатным пустым
  состоянием с безопасной причиной, а неожиданный I/O до публикации
  обрабатывается прежней границей реестра.
- Проверка reload выполняется до файловой работы: требуется ровно один
  `Origin`, совпадающий с нормализованными scheme/host/port текущего запроса,
  разрешённый form media type, фактическое тело не более 4096 байт и ровно
  одно поле с constant-time сравнением токена. CORS не добавлен, TrustedHost и
  CSP сохраняются.
- В дереве `skills/` ровно пять непосредственных каталогов с каноническими
  именами и подписями. Только `meeting-protocol` имеет два дополнительных
  файла `references/example.md` и `references/protocol-format.md`, поэтому
  ожидаемый `has_files=True` принадлежит только ему. Остальные четыре
  артефакта самодостаточны и дают `has_files=False`.

## C. Архитектура относительно канона

Направление `core ← registry ← web` не нарушено: web зависит только от
публичных `Skill`, `LoadReport` и `SkillRegistry`; файлы пяти режимов остаются
данными, не импортируются и не исполняются. Новых LLM, storage, plugin или
repository-абстракций нет.

Jinja2-шаблоны имеют общий `base.html`, локальные CSS/JavaScript и vendor
Bootstrap; недоверенные metadata проходят autoescape, а JavaScript меняет
только `textContent`. Статика смонтирована composition root по абсолютному
пути пакета, поэтому её размещение не зависит от текущего каталога процесса.

Отклонения от канона находятся внутри нового web-класса файлов. Во-первых,
атомарность S3 теряется при добавлении отдельно публикуемого HTTP-summary.
Во-вторых, 351-строчный `routes.py` перестаёт быть тонким адаптером, хотя
утверждённая архитектура прямо требует короткие приватные модули и не требует
собирать DTO, state machine и представление в одном файле.

## D. Читаемость и «Как это работает (просто)»

Имена DTO и ошибок отражают внешний контракт, mapping domain → HTTP явный,
а шаблоны не знают о `Skill.body`. Положительные пути читаются линейно:
factory загружает реестр → route ищет в снимке → mapper оставляет четыре
публичных поля → Jinja строит карточки.

Как это работает (просто): при старте приложение читает пять каталогов и
показывает готовый неизменяемый список. Поиск только фильтрует этот список.
Кнопка reload проверяет источник и токен, в отдельном потоке перечитывает
файлы и затем строит страницу. Ошибка в том, что новый список и подпись
«загружено/пропущено» переключаются двумя присваиваниями: запрос между ними
видит половины разных версий. Большой `routes.py` скрывает это за DTO,
обработчиками и повторяющейся сборкой одинакового контекста.
