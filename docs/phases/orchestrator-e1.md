# Оперативный план эпика E1 «Каркас и каталог скиллов»

Дата: 2026-09-12
Ветка: `main`
Статус: слайсы S1–S4 приняты; публичные контракты зафиксированы как построено

## Понимание эпика

- Пользователь открывает локальное приложение без ключа DeepSeek, видит пять режимов, ищет их по имени или подписи и безопасно перезагружает каталог.
- Поток построен: защищённый FastAPI-каркас → безопасная валидация файлов реестра → атомарное поколение, перезагрузка и поиск → API и серверная страница пяти реальных скиллов.
- Публичная поверхность: `GET /skills?q=`, страница «Скиллы», `POST /skills/reload` с перенаправлением и HTML-предупреждением при недоступности, каталог в формате JSON, один `SkillRegistry` / `RegistryCapture` как источник истины.
- Слайсы зависимы и меняют общий контракт: `E1-S1 → E1-S2 → E1-S3 → E1-S4`.
- Security-scope эпика: **ДА** — HTTP, конфигурация, локальные файлы, YAML, symlink/containment, отображение недоверенных строк и изменяющий reload.
- LLM-scope эпика: **НЕТ** — в E1 нет модельных вызовов, агентов и обработки модельного ответа; содержимое `SKILL.md` только каталогизируется и никогда не исполняется.

## Архитектурное покрытие

Architect: `ba5bd91f-e8b5-4ce0-aee0-c4f76ef170cd`.

- Направление зависимостей: `core ← registry ← web`; `web_ui` содержит только шаблоны и локальную статику; `main → app_factory`.
- `core` владеет конфигурацией, `SkillHubError`, логированием и общим web-security baseline, но не импортирует прикладные пакеты.
- `registry` владеет чтением файлов, containment/symlink-политикой, валидацией, снимком, перезагрузкой и поиском; `web` только переводит фасад в HTTP/HTML.
- HTTP-проверки, CSRF, Origin/Host и представление ошибок принадлежат `web`; RBAC для локального E1 не вводится.
- `app_factory.py` — единственный composition root; `main.py` только публикует собранное приложение.
- Новый поведенческий класс системы — `SkillRegistry`: отдельная сущность оправдана атомарно заменяемым поколением `RegistryCapture` и сериализацией reload. `Skill`, `LoadReport` и `RegistryCapture` остаются неизменяемыми моделями значений. HTTP читает то же поколение и не хранит вторую копию каталога.
- Дополнительные ports, repositories, plugin framework и динамическое исполнение файлов запрещены как преждевременные абстракции.

## Слайс E1-S3 — Атомарный снимок, reload и поиск

- ID: `E1-S3`
- Цель: обеспечить непрерывное чтение неизменяемого реестра при конкурирующих reload.
- Пользовательская ценность: новые скиллы появляются без пересоздания реестра и без частично пустого каталога.
- Зависимости: E1-S2; блокирует E1-S4.
- Тип: backend/concurrency/files.
- Роль реализации: `backend`, `subagent_type: generalPurpose`, изолированное дочернее worktree.
- Skills реализации: `karpathy-guidelines`, `tdd`, `test-driven-development`, `dev-pipeline`, `modern-python`.
- Handoff: `qa-tester`, `security`, `logic-simple`, `perf`, `reviewer`; `ux-client: N/A — клиентского слоя ещё нет`.
- Docs-analyst: после закрытия находок, потому что меняются публичный фасад и поток reload.
- LLM-scope: **НЕТ**.
- Architect: покрыто архитектурным резюме; границы registry неизменны.

### Договор E1-S3

Критерии приёмки:

1. Когда создан реестр, читатель получает неизменяемый snapshot и не может изменить его извне.
2. Когда reload завершается, полностью собранный новый snapshot заменяет старый одним присваиванием; частичное состояние не публикуется.
3. Когда несколько reload идут одновременно, один lock сериализует только reload, а чтение snapshot и поиск не берут этот lock.
4. Когда четыре читателя работают параллельно с повторными reload, они видят целиком старый или новый непустой snapshot и не получают исключений.
5. Когда выполняется поиск, name и caption сравниваются case-insensitive, а результат имеет стабильный канонический порядок; отчёт содержит loaded/skipped.

| Риск | Наблюдаемый исход |
|---|---|
| Успех | Новый корректный каталог появляется после reload. |
| Отказ | Битый шестой каталог попадает в skipped, пять корректных остаются в опубликованном снимке. |
| Неверный ввод | Пустая или отсутствующая директория даёт предсказуемый пустой отчёт, а не 500. |
| Правило домена | Только reload меняет ссылку на snapshot; читатели не мутируют модели. |
| Повтор | Повторный reload без изменений идемпотентен и сохраняет порядок. |
| Атака | Конкурентный вызов не публикует частично проверенные данные и не обходит файловую политику S2. |

Канон репозитория:

- `docs/architecture/skillhub.md` — copy-on-write sequence и lock-free readers.
- `CONTEXT.md` — определения снимка и reload.
- `docs/phases/epic-e1-foundation-registry.md` — поиск и четыре читателя.
- `docs/security/threat-model.md` — целостность каталога.

Шаги реализации: TDD неизменяемости и порядка → атомарная публикация → сериализация reload → многопоточный тест без временных ожиданий как оракула.

Тесты договора: immutable mapping; old/new snapshot; concurrent reload; четыре читателя; stable case-insensitive search; missing directory; valid+broken catalog.

## Слайс E1-S4 — Пять режимов, API и веб-каталог

- ID: `E1-S4`
- Цель: показать пять реальных скиллов через единый фасад в JSON и серверном UI.
- Пользовательская ценность: режимы видны, ищутся и безопасно перезагружаются.
- Зависимости: E1-S3.
- Тип: mixed backend + frontend.
- Роль реализации: `backend`, `subagent_type: generalPurpose`, изолированное дочернее worktree.
- Skills реализации: `karpathy-guidelines`, `tdd`, `test-driven-development`, `dev-pipeline`, `fastapi`, `feature-frontend`, `insecure-defaults`.
- Handoff: `qa-tester`, `security`, `logic-simple`, `perf`, `ux-client`, `reviewer`.
- Docs-analyst: после закрытия находок, потому что появляется публичный HTTP/API/UI-поток.
- LLM-scope: **НЕТ**.
- Architect: покрыто архитектурным резюме; web использует существующий фасад registry.

### Договор E1-S4

Критерии приёмки:

1. Когда приложение стартует на штатном `skills/`, `GET /skills?q=` и страница «Скиллы» показывают ровно пять утверждённых режимов с caption, name, description и `has_files`.
2. Когда задан query, единый поиск фасада фильтрует name/caption case-insensitive и сохраняет стабильный порядок в API и UI.
3. Когда пользователь запускает reload с корректным CSRF и same-origin запросом, форма перенаправляет на страницу «Скиллы» и показывает понятный loaded/skipped результат; каталог обновляется из того же поколения реестра. Если допуск занят, браузер остаётся на каталоге с HTML-предупреждением.
4. Когда появляется битый шестой каталог, reload сохраняет пять корректных режимов и показывает безопасное предупреждение без тела файла.
5. Когда metadata содержит HTML/JavaScript, Jinja autoescape и клиентский код отображают его как текст; CSP, TrustedHost, CORS off и localhost bind остаются включены.

| Риск | Наблюдаемый исход |
|---|---|
| Успех | API и UI показывают один и тот же список пяти режимов. |
| Отказ | Отсутствующий каталог даёт пустой экран/API и понятное предупреждение, не 500. |
| Неверный ввод | Длинный или пустой query обрабатывается предсказуемо и не меняет snapshot. |
| Правило домена | Файлы скиллов — данные; web не импортирует и не исполняет их. |
| Повтор | Повторный reload идемпотентен и не дублирует карточки. |
| Атака | Reload требует CSRF/same-origin; metadata не исполняется как HTML; ошибки не раскрывают локальные абсолютные пути. |

Канон репозитория:

- `docs/architecture/decision-rationale.md` — Jinja2 + локальный Bootstrap + обычный JavaScript.
- `docs/security/threat-model.md` — XSS, CSRF, CORS, TrustedHost и недоверенные строки.
